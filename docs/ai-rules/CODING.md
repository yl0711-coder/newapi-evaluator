# api中转站：AI 编码共用规范

状态：正式规则 v1.0。用户已授权启用；适用范围与操作权限见 CODING.md。

## 目标与适用方式

为渠道质量、测试工具和任务可靠性建设可维护、可验证的代码；每次改动都与当前需求对应。

适用于 `api中转站` 内的维护项目。同时按仓库身份绑定 `https://github.com/yl0711-coder/newapi-evaluator`：对此仓库进行开发、修复、测试、审查、Git 或发布等操作时，均须遵守适用条款，不受本地目录名称或位置、设备、分支、Tag、detached HEAD 或 worktree 形式影响。已确认来源于该仓库的克隆和检出副本同样适用；改名、移动目录或更换检出形式不能绕过规则。只读与验收副本保持其原有写入限制，具体操作权限按 G6 判断。

继承适用的上层规则与用户明确指令；子项目规则说明更具体的条件与执行入口。规则冲突时先核对作用范围，不默默选用更宽松的一条。

## G1 开工依据

先读取相关 README、项目规则和当前任务状态；核对仓库身份、真实路径、分支、HEAD、未提交修改和实际调用关系。仓库身份结合用户指定对象、远端与已知 worktree/检出来源核实，不能仅凭目录名或远端是否叫 origin 判断。记录适用规范的入口与版本；只携带与任务有关的上下文。可从代码或环境查到的事实由 AI 核实。

## G2 任务范围

开工简述目标、修改范围与验收方法；需求清楚后连续实现、验证并交付。计划外发现记为独立事项。必须扩大范围时先给出原因、受影响接口/数据和具体方案；现有授权不能覆盖扩展内容时，取得用户对该具体范围的明确指示后再实施。已授权目标内的必要实现与修复不重复确认。

## G3 模块与业务定义

先找已有实现与业务定义的维护位置。同一业务规则在一处维护，其他模块通过明确接口引用。新增共享层必须有实际调用需求；不为假设中的扩展性增加框架。变更前核对调用方和下游消费者。

`中转站极限测试实验室` 是 `模型测试工作台` 的功能子集，也是该子集的主维护来源。该范围内的修改和新增功能默认先在实验室开发、验证，再按 [T8 两阶段集成流程](TESTING.md#t8-实验室先行与工作台集成) 进入工作台。工作台独有功能在所属模块维护；具体任务明确只做实验室试验时，遵循该范围。两边不得各自维护相互冲突的同一业务规则。

## G4 修复与重构

修复先定位触发条件和根因，证明改动如何解决问题。只修改达到目标所需的代码，避免夹带全仓格式化、迁移目录或无关重构。必要的协议分支、错误处理、数据迁移与兼容适配不因“纯净”被删除。

## G5 代码与接口

新增后端业务逻辑统一使用 Python，新增 Web API 统一使用 FastAPI；前端沿用现有技术栈。引入其他后端语言或 Web API 框架须说明理由和影响，并获得用户同意。已有其他实现不因本规则自动重写；各项目记录实际运行时、依赖版本和已有例外。

遵循子项目现有命名、格式与类型配置；名称表达业务含义，职责与依赖方向清楚。注释说明原因与约束，接口文档说明输入、输出、错误和使用方式。对外 API、配置、数据库及报告字段的变更同步更新契约、调用方、相关测试和文档。

新增或移动规则、测试入口和文档时，核对实际读取入口、测试注册、源码允许清单及打包范围；需要更新的配置随改动一起维护，不能仅添加文件就宣称已接入，也不能为消除扫描失败而扩大无关允许范围。

## G6 数据与执行边界

产品代码只写本次任务所属目录。独立验收副本仅检出指定提交并验证，不编辑业务代码。本机运行数据、日志、临时文件、依赖环境及报告沿用统一目录 `/Users/lmurder/Desktop/api中转站/中转站极限测试数据`；子项目已有明确有效的专项授权按其范围执行。其他设备或 CI 在该环境专项配置中明确映射仓库外的隔离产物目录，保留源码、业务数据与测试产物的隔离要求，不照搬本机绝对路径，也不因映射缺失而回落到源码或业务数据目录。正式落地不得自行搬迁现有服务数据。

保留用户已有改动、业务数据、备份和历史证据；不覆盖、重置、删除或移动用户文件，不改任务外项目。发现外部活动造成的变化，只记录已核实事实，不把“本轮未写入”说成“期间完全未变化”。

任何代码、Git、日志、报告、JSONL、聊天或外发材料不得含 API Key、凭据、Token、Cookie、完整敏感 URL/查询参数或可识别客户信息。产品报告按用户确认的 [REPORTING.md](REPORTING.md) 保留既有题目、回答、技术证据及展示、保存和下载能力；不以共用正文禁令删减已有功能。该范围外的运行日志、开发/验收证据、Git、聊天与新增外发材料仍不得包含 Prompt 或原始请求/响应正文，只使用白名单脱敏指标和必要摘要；独立编写、无真实业务来源且不含敏感信息的自动化回归夹具按 REPORTING.md P3 的明确条件允许入库。无法确认脱敏时不传播原始材料。

修改已有子功能和新增功能均在 `feature/*` 或 `fix/*` 分支进行；已有对应任务且已获授权的分支可以继续使用，不在 `main` 直接开发或提交业务改动。分支开发完成后，先完成适用测试和独立审查，向用户提供候选版本、目标分支、完整改动和验证结果；用户明确允许该次合并后，才合入对应目标分支。测试、审查通过或要求“完成开发”均不自动构成合并许可。

为完成获授权的开发与验证，可以在隔离的功能/集成分支准备候选结果；未经该次合并许可，不把候选变更写入目标交付分支，也不通过直接复制、cherry-pick 或其他操作绕过该边界。请求许可前先把候选结果做成可审阅、可验证的状态。已明确允许的同一次合并按其范围执行，不重复确认；候选变更超出已批准范围时先重新验证并取得新增范围的明确允许。

没有对应授权，不 push、创建 PR、修改远程或重写历史；合并许可不自动包含远端推送、Tag 发布或部署。子项目已获授权的远程和分支只在其范围有效，不能复制为其他项目权限。`main` 仅在用户明确指定其为该次合并目标时接收已验收变更，仍禁止直接开发。

开发验收默认使用隔离 Mock；真实接口须用户明确授权与 `--confirm-live`。界面确认方式如有不同，必须在子项目专项条款中明确，不能自行视为等价。禁止通过重定向或环境代理绕过限制；破坏性/崩溃注入仅限本地 Mock 或明确授权的隔离目标。外部通知与真实测试不混入普通自动化验证。测试平台不自动更改中转站配置、路由和权重。

既有目录、数据、Git 和网络专项限制继续适用；本次用户已明确更新的维护顺序、报告兼容和合并条件以本正式版本为准。旧流程仅作执行参考，不自动取得远端或其他项目权限。

## G7 验证与独立审查

每次代码交付执行 [TESTING.md](TESTING.md)；测试代码和测试入口本身也受审查。开发方自查后，按 [REVIEW.md](REVIEW.md) 交给独立审查任务，再修复并复核。全量检查缺项、独立审查未完成或必修项未解决时，不能宣称全部完成。

开发与独立验收按 [HANDOFF.md](HANDOFF.md) 交接候选版本、可执行入口和证据。规则只在各自文件定义；开发/验收角色入口引用同一套规则，不另复制一份逐渐分叉的流程。

## G8 状态与文档

规则变化就地更新唯一规则源，变更历史保留在版本记录；任务状态只维护当前目标、进度、下一步和未决事项，并引用版本与证据位置。续接先核对实时状态，不把历史通过记录当作新版本证据。清理仅限本次产生且已确认无用的代码残留。

## G9 测试产品的结论边界

指标必须明确单位、分母、样本条件、起止时间和缺失值语义。`null` 不解释为零；字符不冒充 token；客户端在途不冒充服务端生成并发；Mock 不证明真实容量。渠道稳定性、流式传输完整性和工作台任务恢复能力分别评价。具体阈值与协议完成语义由子项目维护。
