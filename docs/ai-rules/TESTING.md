# 全量测试规范

状态：正式规则 v1.0。用户已授权启用；适用范围与操作权限见 CODING.md。

## T1 全量的定义

全量通过 = 本次版本适用的所有必需测试组都完成并通过，且没有未处置的跳过、漏跑、超时或不稳定失败。

已确认的跨项目范围：

- 每次代码交付，当前修改的项目运行全部适用的必需测试组。
- 对受影响的其他项目，验证涉及的功能、接口与集成链路；涉及公共能力时覆盖已识别的消费者。
- 跨项目改造或统一发布时，对涉及的所有项目运行全部适用的必需测试组。

范围无法确定则先分析依赖，不能随意缩小。历史存档和重复验收检出不当作独立产品重复测试；独立验收仍按 T5 执行。

每个项目维护一份测试清单，记录 suite_id、负责验证的需求/规则、入口、依赖、触发条件、时间上限、结果位置和适用环境。新增功能同步补清单；调整清单与触发条件必须接受独立审查。命令不存在或必需依赖未准备，不得标记为“不适用”。

按项目约定的测试文件或框架发现规则，将实际用例与注册清单对照。新测试未接入、注册入口已不存在、被遗漏的既有套件均须明确处理；有意排除的套件记录原因和触发条件，不能仅凭入口名称含“all”宣称全量。

## T2 测试层次与触发

| 测试组 | 验证内容 | 运行条件 |
| --- | --- | --- |
| 静态与安全 | 子项目规定的语法、类型、格式、敏感信息检查 | 每次代码交付；没有配置的检查如实登记，不伪称已通过 |
| 单元与领域行为 | 输入边界、业务规则、错误归类、统计口径 | 每次代码交付运行完整既有套件，并加入本次必要回归 |
| 接口与模块集成 | API/配置/数据库契约，调用方与状态变化 | 每次代码交付执行项目登记的必需集成套件 |
| 本地端到端 | 实际 HTTP/SSE 请求经过解析、执行、持久化和报告 | 核心测试流程的必需链路每次交付运行；额外场景由清单声明 |
| 浏览器 | 用户操作、运行状态、错误反馈、报告与导出、必要的窄屏检查 | 页面交互变更必跑，并保留项目已规定的常规 UI 套件 |
| 构建与部署形态 | 构建成功、容器启动/健康、静态资源、版本对应 | 构建/依赖/启动配置变更或准备发布时，及项目原有更严格条件 |
| 容量与长时可靠性 | 在明确负载、时长、环境下观察资源与恢复 | 按项目注册配置执行；真实压力和长期实测不自动混入日常 Mock 验收 |

纯文档修改检查准确性、链接、示例和格式。修改测试清单、执行脚本或 CI 属于执行机制变更，须验证新增路径、失败路径和结果聚合，不能套用纯文档豁免。

## T3 本项目的场景清单起点

这是需要映射到真实测试用例的需求清单，不宣称每项已实现或已覆盖。只对项目实际提供的功能声明适用性。

| 业务区域 | 必须有可观察结果的场景 |
| --- | --- |
| 公共渠道 | 新增/编辑/停用，密钥留空保留与替换，任务引用有效性；不因保存渠道自动创建计划或判定上线 |
| 准入 | 候选/参照隔离、预热样本规则、失败与停止、报告一致性、临时凭据不落盘 |
| 稳定性 | 计划开始/通知时序、单调度器约束、实际请求上限、历史基线采样条件、超时/断流/错误归类 |
| 非流式 | 有效/空/损坏响应、可见字段、结束/截断信号、报告导出范围 |
| 协议 | 每种宣称支持的协议及响应模式的正常结束、半途断流、格式错误、限流/5xx、首段/空闲/总超时 |
| 极限与指标 | 单号入池门槛、号池/网关场景、固定批次/持续负载/实时推子各自语义，百分位/分母/缺失值/低样本 |
| 长任务恢复 | 成功步骤与检查点一致提交，重试预算、取消、进程中断后继续、未确认结果、配置变更拒用旧检查点 |
| 数据兼容 | 无真实数据的旧结构夹具、重复初始化、迁移后不丢已有字段与关系、旧报告可读 |
| 产品报告兼容 | 按 REPORTING.md 的既有功能验证展示、历史读取、各类导出及脱敏边界，不把所有报告统一裁减为指标或统一扩展为保存正文 |
| 隔离与泄漏 | 测试不触达未授权上游或通知端，不读取真实业务库；持久化与导出不含凭据及禁止内容 |

稳定性模块的请求上限和极限测试的可配置并发属于不同业务规则，不得在共用规范里合并成一个全局常量。不同协议的结束条件也不一刀切。

## T4 测试代码质量

- 用需求/业务契约给出预期，主要断言可观察结果；关键算法使用独立预期样例，不调用被测算法算期望值。
- 缺陷修复应有能复现原问题的回归检查；必要时在隔离旧版本或定向故障下确认测试真的会失败。
- 不用函数名存在、源码字符串包含或固定调用次数替代业务正确性；确需验证内部性能/缓存行为时说明理由。
- Mock 只替换外部依赖和不可控条件，保留应验证的真实解析、状态、事务与报告链路。分别测试 Mock 契约与真实适配入口。
- 时序测试使用事件、状态或可控时钟；必须真实等待时设置有依据的范围和明确超时。禁止随意扩大阈值、删断言或循环重跑掩盖不稳定。
- 用例彼此隔离，资源在成功、失败和取消路径均关闭；不依赖测试顺序或上一次运行的数据。
- 代码覆盖率可辅助找遗漏；不把百分比或测试数量作为正确性证明，也不为数字编写无效测试。

## T5 隔离与执行

按子项目登记的解释器、依赖、端口与数据目录运行。正式独立验收使用指定的干净提交、独立环境和全新数据目录，不复用开发缓存、业务数据库或旧结果。

测试默认不发真实外部请求或通知。用合成输入与本地 Mock；出站限制、超时、取消及故障恢复通过实际路径验证。真实接口测试单独登记授权目标、负载和停止条件，不把未开展的真实验证写成通过。

统一入口必须逐组汇总命令、退出码、执行/失败/跳过数量和状态。子进程失败或超时不得被汇总成功覆盖；提前停止后未运行的组明确标为 not_run。发现零用例、缺少必需组、收集失败或未知退出状态时，不能输出全量通过。

成功判定同时核对子进程正常退出、框架结果和收集完整性；输出中出现“通过”或“失败项：无”不能覆盖非零退出码、崩溃、失败断言或结果缺失。保留必要且已脱敏的标准输出与错误输出，不能丢掉错误通道后只解析成功文字。

首次失败保留；重跑记录原因和全部尝试。一次失败后偶然成功不等于已定位并解决问题。临时隔离不稳定用例必须有原因、影响、负责项和恢复条件，不得由 AI 为交付静默豁免。

每组应登记单次超时和整体预算；依据实际基线调整并说明原因。执行器必须实施这些时间上限，不能只写在文档或配置中。预算耗尽保留结果、终止本测试创建的进程并报未完成，不终止其他服务，不通过无限重试追求绿灯。

清理前核对资源确属本次测试、解析后的实际路径位于已分配的测试目录，并检查所有登记的数据库、旁路文件、备份与子进程。清理失败或路径身份不明时停止该阶段并保留证据，不提示用户删除业务数据库或按进程名称批量杀服务。清理错误不能被最终成功状态覆盖。

## T6 结果语义

| 状态 | 判定 |
| --- | --- |
| passed | 必需组和必需用例全部完成并通过，无未解决的执行缺口 |
| failed | 有业务断言、安全边界或必需检查确定失败 |
| incomplete | 环境阻塞、未运行、超时、必需跳过或证据缺失；不能说全部通过 |
| not_applicable | 清单预先定义的条件不适用，并附具体依据；不能用于隐藏失败 |

发生多种状态时保留所有明细，有确定失败则总体 failed，其他必需缺口则总体 incomplete。JUnit/unittest 的成功退出必须结合收集、跳过及测试清单检查后才可转成全量 passed。

若历史失败阻塞全量，记录基线对照和影响：本次未引入该失败不代表全量通过；历史修复另建任务，开发 AI 不自行扩大范围。用户可以明确接受具体历史问题的交付例外，但质量状态仍保留 failed 或 incomplete，另记“用户接受例外交付”。例外记录必须包含问题 ID、项目及候选版本、影响、接受的阶段与范围、用户指示证据和后续处理项；只对该范围和版本有效，不自动覆盖后续版本或新问题。其他必需检查、本次引入问题的修复和独立审查仍须完成。例外不自动放行 T8 的下一阶段，也不包含合并、推送或发布许可；若确需在具体缺口下继续某阶段，必须另有明确覆盖该阶段的用户指示，并保留缺口和质量状态。

## T7 证据与版本

每次记录：基线与待测版本、规则/清单版本、环境与依赖指纹、脱敏配置、命令和时间、逐组状态、用例结果、失败摘要、相关产物路径，以及未验证边界。

开发中有未提交修改时，用 HEAD 加 diff/必要文件指纹准确标识快照，不伪称只测试了 HEAD。正式提交验收绑定实际 40 位 SHA；验收后源码变化必须重新评估并验证，旧证据保留为历史。测试、审查和发布如有执行，应可追溯至同一候选版本。

交付或记录验收结论前，再核对目标候选版本。使用 PR 时核对其当前 head；已变化则将现有报告标为原 SHA 的历史结果，不能替新版本给通过结论。受影响检查是否重跑按 R6 判断，新版本结论须有对应依据。

本节的开发与验收报告只保存白名单脱敏指标、必要摘要和证据定位；产品自身生成的报告按 [REPORTING.md](REPORTING.md) 保持现有功能，两者不能混用。验证题目、回答或原始响应的展示与导出时使用合成夹具，不把真实报告正文复制进测试日志或 AI 审查材料。源码扫描、异常栈和工具日志也可能含敏感内容，保存/传播前脱敏。Pristine 扫描只提供线索，不替代类型、安全、业务测试或人工判定。

## T8 实验室先行与工作台集成

按 [G3 的维护关系](CODING.md#g3-模块与业务定义) 执行，流程包含两个可分别追溯的阶段：

1. 实验室阶段：在该子集的主维护代码中实现修改或新功能，完成相关测试、实验室全量测试、安全检查、开发自查、独立审查及修复复核。存在必需检查缺口或未解决的必修项时，不进入工作台集成阶段。
2. 固定来源：记录通过验证的实验室版本、改动范围及证据。正式提交按 T7 绑定完整 SHA；核对工作台目标基线和既有未提交改动，再确定集成涉及的文件、接口与必要适配。
3. 工作台候选集成：在获授权的独立功能/集成分支准备已验证的相关变更及必要适配，保留工作台其他功能和用户已有改动，不用实验室目录整体覆盖工作台。这里用于形成可验证的候选结果，不直接写入目标交付分支。集成中发现共享业务逻辑需修正时，回到实验室修复和验证后重新准备候选；工作台专属适配在工作台维护。
4. 工作台验证：对集成后的实际版本运行工作台完整必需测试组、安全检查和独立审查，按 T1 验证受影响项目；页面交互改变时追加浏览器验证。重点覆盖模块挂载、鉴权、共享配置或渠道引用、数据隔离及实际受影响的调用链。实验室通过不能替代工作台通过。
5. 提交合并审阅：同时给出实验室来源版本、工作台候选集成版本、目标分支、两阶段测试与审查证据、修复和未完成项。依 T7 保持证据与最终源码一致；已授权的开发、候选准备、测试和审查连续推进。实际合入任一目标交付分支前，按 G6 等待用户对该次合并的明确允许；不得把“两阶段流程已确认”解释为自动合并许可。合并及目标版本变化后的验证范围按 T7/T9 核对，远端操作与发布仍受各自授权约束。

## T9 本地检查与 CI

本地、独立验收与 CI 按同一测试清单说明各自覆盖范围；不同平台或缺少能力造成的执行差异须显式登记。CI 通过仅证明该次实际运行的组，不替代未运行的浏览器、独立验收或其他必需检查。

核对流水线的触发条件、实际检出版本及允许清单，不能假定每个功能分支、每次推送或每个 Tag 都已跑完整测试。CI 若测试的是合并候选提交，分别记录 PR head 和实际受测 SHA。源码新增规范文件、测试或发布入口时，验证它们能被读取、收集及纳入正确产物。

准备发布时，按适用清单核对候选源码的有效测试与审查证据，并验证实际构建产物；只运行安全扫描的发布任务不等于完整验收。若已获授权发布镜像，记录源码版本、镜像标签和不可变 digest 的对应关系。创建或推送会触发发布的 Tag 按 G6 的远端/发布授权处理，不把它当作无副作用的版本标记。
