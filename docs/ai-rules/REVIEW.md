# 独立审查规范

状态：正式规则 v1.0。用户已授权启用；适用范围与操作权限见 CODING.md。

## R1 审查时机与范围

规范确定后，按项目分批开展存量审查并汇总；每次代码修改审查全部改动及相关调用链；跨模块变更扩大到接口消费者、数据和部署契约。报告列出已审、未审、抽查和不适用范围；不能用一次关键词搜索宣布全项目合规。

## R2 开发与审查职责

开发方先完成自查和测试。独立审查方使用独立任务上下文，读取用户目标、适用规则、待测快照、完整改动、相关代码和测试证据；核实开发结论，不把开发方解释当作事实。

交接内容与正式验收记录使用 [HANDOFF.md](HANDOFF.md)。没有 GitHub PR 的本地任务使用同样的版本和证据字段，不为满足模板而创建 PR 或向外发送报告。

审查方不编辑业务代码、不替开发方提交或发布。需要验证疑点时在允许的隔离环境执行聚焦复现。开发方负责获授权范围内的修复，再由审查方复核最终版本。独立审查未执行时，不能用开发方再读一遍冒充。

## R3 必查内容

| 维度 | 具体问题 |
| --- | --- |
| 目标与结构 | 是否完成约定目标，是否夹带范围外改造，新增后端是否遵循 G5 的 Python/FastAPI 约定或已有明确例外，业务规则是否重复定义，依赖/模块职责是否变得混乱 |
| 正确性与边界 | 正常、异常、取消、并发、重试、资源清理及状态转换是否符合契约 |
| 接口与数据 | 调用方是否兼容，迁移和旧报告是否可用，事务/检查点是否保持一致 |
| 测试与证据 | 适用组是否齐全、注册是否漏项、断言是否有效、退出码与汇总是否一致、是否隐藏失败或跳过、证据是否对应最终改动 |
| 安全与产品结果 | 出站/凭据/数据目录是否符合限制；是否按 REPORTING.md 保留既有报告能力及各导出版本的区别，指标语义和文档是否同步 |

代码风格以项目明确规则和工具为依据；未规定的个人偏好不能自动升级为缺陷。算法/协议/公共 API 的必要说明不能仅因属于解释性文字而删除。

## R4 问题必须可核对

```text
问题 ID：
适用规则：
文件与最小定位范围：
触发条件与证据：
实际行为 / 预期行为：
影响与严重程度：
本次引入 / 历史已有 / 尚未确定：
修复建议及验证方法：
状态：待核实 / 待修复 / 已修复待复核 / 已复核 / 历史待办
```

不能只写“可能有风险”“不够纯净”或“建议重构”作为阻塞项。不能证明的疑点列为待核实，并说明需要什么证据。关键词命中需阅读上下文；动态注册、反射、外部入口或导出 API 不能仅因文本调用少判成死代码。

## R5 处理与完成条件

用户已确认：本次改动引入的功能错误、数据/兼容性问题、越界修改及硬性规则违规必须修复并重新验证。开发方在已授权任务范围内自行完成这些修复。

历史问题记录位置、影响和优先级，不自动启动全仓整改；若影响本次任务成立或全量检查，明确报告阻塞关系。纯改进建议单列，不伪装成硬性违规。历史问题或范围外整改须由用户明确纳入具体任务后实施；说明方案本身不构成授权。已授权目标内的必要修复直接推进，不新增逐步批准环节；其他范围扩展按 G2 处理。

正常代码交付完成要求：所有必修项复核关闭、[T6](TESTING.md#t6-结果语义) 的必需检查为 passed、独立审查覆盖完成。未达到时如实给出 failed 或 incomplete 及原因。若用户依 T6 明确接受具体历史问题的例外交付，独立审查仍核对其他检查、必修项和例外记录，结论写为“用户接受例外交付”，不得写成全量通过或无条件完成。测试与审查状态、交付接受状态和 Git/发布授权分别记录；审查或例外接受不自动授权合并、推送或部署。

## R6 最终报告

报告包含目标与实际版本、规则版本、范围、检查结果、问题清单、修复复核证据、历史待办和未验证边界。没有发现问题应写成“在所列范围和方法内未发现阻塞问题”，不宣称没有任何缺陷。

整改后先复核问题与受影响用例，再按清单执行最终必需检查；源码未变且证据有效的检查不无理由反复重跑。若修复改变待测版本，重新核对适用范围并绑定新证据。
