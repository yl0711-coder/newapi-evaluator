# New API 渠道自动监控

工作台 `/channel-monitor/` 为 `v1.0.0-rc.26` 提供半小时直测及单渠道启停。默认暂停；保存管理连接和映射不会发模型请求。管理令牌与公共渠道模型 Key 分开加密保存。管理连接需要 ChannelRead、ChannelOperate 权限，模型调用令牌不能替代管理令牌。

每道题最多发送五次（首次加四次重试）。断联、超时、空响应及上游 HTTP 错误可重试；五次都实际记录为请求失败后停用，忽略四条保护。程序中断、出口拒绝、取消、配置漂移、未知结果、评分格式无效均不能凑成五次失败。有效回答立即停止重试，不因答错继续刷题。

正常渠道先测已有 hard-3 糖果题。只有答错才追加三个固定 ModelTrace 探针。连续两个相邻半小时轮次均为糖果答错且 MT 明确不匹配，才申请停用；无效或无法判定会中断连续计数。逐条停用前重新读取完整库存，检查该渠道所有模型及分组，停用后每个组合须至少四条已启用渠道；不足时保留渠道并在页面告警。API 指纹尚未校准，结果是闭集行为信号，不能认证真实模型权重。

停用仅修改 New API 状态，不停用 Eval 公共渠道。系统因请求故障停用的渠道，下一次糖果请求正常即恢复；因质量停用的渠道，下一次糖果答对且 MT 匹配即恢复。只恢复系统有确认写入和回读记录的渠道；人工锁定、外部停用、配置变更及状态写入结果未知均保留待处理。暂停计划停止后续发送；已经许可的管理写入可能已执行，须查看动作账本。

配置时精确指定 New API 渠道 ID、Eval 公共渠道 ID、模型和协议，不按名称猜测。当前支持单密钥、无额外参数/请求头转换的 type=1 OpenAI 兼容渠道；地址、模型映射及连接指纹须一致。rc.26 普通渠道读取不提供密钥，操作人须核对两边使用同一把上游 Key；后台换 Key 后须暂停并重新绑定。rc.26 状态接口没有 CAS 或独立自动化所有者标识；自动操作在本实例内串行执行，外部同时修改库存无法获得跨系统事务保证。人工维护前使用页面锁定或暂停。

管理读取等待结束后重新读取公共渠道状态与连接；模型发送及管理动作的最终许可，在同一 Registry 写事务内复核启用状态、连接指纹与精确模型映射。等待期间停用渠道、换 Key 或改变映射会阻止后续发送和启停，不记为渠道故障，也不认领停用所有权。

适配依据为官方 rc.26 的 [渠道模型与状态写入](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.26/model/channel.go)、[管理控制器](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.26/controller/channel.go) 及 [渠道设置](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.26/relaykit/dto/channel_settings.go)。仅允许已核对的空值和默认设置；组织头、代理、系统提示、透传、参数/请求头/状态码转换及未知设置拒绝绑定。启停自身更新的 `other_info.status_reason/status_time` 不计入连接指纹，其他配置仍参与漂移检查。动作账本冻结实例指纹、渠道 ID、模型协议及检测条件，移除映射或更换管理连接不会改写历史目标。

排期复用 Eval 现有稳定性调度器和数据目录锁。保存启用计划后从下一个半小时时隙开始，按开始到开始计时；原时隙 1100 秒窗口不延长，错过直接跳过，不补测、不创建漏轮。立即测试不改变半小时锚点。所有模型请求复用共享传输与发送容量，长耗时可能使部分目标在本轮未测，不能将其判为故障。

复用依据是用户指定的「建立每20分钟渠道定时测试计划 (2)」及其 `定时测试-20261010` 独立执行器：末行整数判分、独立尝试身份、固定开始计时、原窗口截止、完整 usage 和中断保留。历史运行配置、密钥、账本、冻结 runtime 和原生 heartbeat 保持独立；新模块没有导入或改写这些运行文件。历史脚本的 401/403/404 提前停止和一次指纹重试不作为本模块五次故障门槛。

只读检查：`python -B -m features.channel_monitor inspect-config`。只输出规则与配置指纹，不打开数据库、不读凭据、不联网。

开发与独立验收使用 `scripts/verify_integrity.py` 注册清单，新增 Python 状态机/管理协议回归、只读检查和浏览器交互。全部使用合成输入与本地 Mock；不证明真实管理权限、真实模型身份或生产调度已经启用。
