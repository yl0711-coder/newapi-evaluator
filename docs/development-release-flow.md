# 开发、验收、发布与清理流程

状态：项目级流程 v0.1

适用范围：`yl0711-coder/newapi-evaluator` 在本机的功能开发、OrbStack 验收、镜像发布和本地清理。

本文件补充 `docs/ai-rules/` 的正式共用规则，不替代编码、测试、审查、交接和发布授权规则。单设备可以完成开发与独立验收；“独立”指版本、任务上下文、依赖环境、数据目录和证据隔离，不要求第二台设备。

## 1. 固定角色与边界

- `/Users/lmurder/Desktop/eval` 是新功能的主要开发工作区。
- 功能修改在 `feature/*` 或 `fix/*` 分支进行，`main` 只作为干净基线和候选合并目标。
- 开发、独立验收和 OrbStack 运行可以使用同一台设备，但不得复用开发缓存、业务数据库或旧验收结果。
- 运行数据、日志、数据库、密钥、虚拟环境和验收证据放在仓库外；本机统一沿用 `/Users/lmurder/Desktop/api中转站/中转站极限测试数据` 下的项目隔离目录。
- 默认使用本地 Mock。真实上游、真实通知和生产配置变更仍需本次明确授权。

## 2. 版本身份

每个候选版本必须同时记录：

- 40 位源码 SHA；
- 分支和候选阶段；
- 功能镜像或集成镜像 Tag；
- 镜像不可变 digest；
- OrbStack 容器名、端口和数据挂载；
- 测试结果、未验证边界和外置证据目录。

验收不使用 `latest` 作为唯一身份。`latest` 可以作为 CI 的附加发布标签，但最终测试必须绑定版本 Tag 和 digest。

## 3. 标准流程

### 阶段 A：功能分支开发

1. 核对基线 SHA、工作区状态和适用规则。
2. 在功能分支实现子功能，补齐必要的单元、契约、集成或页面测试。
3. 执行本项目适用的静态、安全和测试检查，保留失败、跳过和未运行项。
4. 形成开发候选记录，不直接修改 `main`、NewAPI 配置或生产环境。

### 阶段 B：独立功能容器

1. 从功能分支构建带有功能名和短 SHA 的本地镜像。
2. 在 OrbStack 中创建独立功能容器，不覆盖其他项目容器和数据卷。
3. 核对实际运行镜像、容器健康状态、端口、环境变量和数据挂载。
4. 交给用户测试功能表现。

### 阶段 C：问题修复循环

用户提出问题后，回到功能分支修复；修复后重新绑定新的源码 SHA，重新构建镜像并重新测试。旧镜像和旧证据只能作为历史记录，不能替代新版本验收。

### 阶段 D：主项目候选集成

1. 功能容器通过后，将变更集成到主项目候选分支或获授权的目标分支。
2. 运行主项目适用测试，并构建集成候选镜像。
3. 在 OrbStack 中重新创建候选容器，验证模块挂载、鉴权、共享配置、数据隔离和现有功能回归。
4. 用户确认主项目表现无异常后，才视为本次合并许可；测试通过本身不自动授权合并。

### 阶段 E：Tag 与 CI 镜像

1. 用户确认发布版本号，例如 `v1.8.0`，并明确允许本次 Tag 和推送。
2. 将 Tag 绑定到已验收的完整源码 SHA，推送到 `https://github.com/yl0711-coder/newapi-evaluator`。
3. 等待 CI 完成自动测试、容器健康检查和多架构镜像构建。
4. 记录 CI 生成的版本 Tag、源码 SHA 和镜像 digest；CI 失败时不得进入下一阶段。

### 阶段 F：发布镜像最终验收

1. 按版本 Tag 拉取镜像，不以本地旧镜像冒充远端构建结果。
2. 核对拉取后的镜像 digest 与 CI 记录一致。
3. 使用 `--force-recreate` 或等效方式重新创建 OrbStack 容器；仅 `docker pull` 不代表运行中容器已更新。
4. 保留既有数据挂载，执行用户最终功能测试。

### 阶段 G：Linux 上线

只有用户明确确认最终镜像测试无异常后，才进入 Linux 上线。上线前记录生产服务器、镜像 digest、配置版本、数据备份和回滚镜像；上线后核对健康状态、端口、日志、数据挂载和关键功能。

## 4. 清理顺序

发布确认完成后，只清理本次流程产生且已经确认无用途的资源：

1. 停止并删除本次功能容器和候选容器；使用项目名称或标签精确筛选，不清理无关容器。
2. 删除本次功能的临时镜像、悬空镜像和确认不再需要的本地副本。
3. 清理本项目可识别的构建缓存和临时导出目录。
4. 保留当前生产镜像、上一稳定版本镜像、镜像 digest、发布记录和回滚所需配置。
5. 最后核对容器、镜像、卷、挂载、Git 状态和外置证据目录。

默认不使用以下命令：

```bash
docker system prune -a --volumes
git clean -fdx
```

它们可能删除其他项目的容器、镜像、卷、未追踪源码、`.env`、数据或证据。`docker compose down` 默认不带 `-v`，除非已经确认卷内没有业务数据且有可恢复备份。

## 5. 工作区清理边界

- 可以清理本次生成的 `__pycache__`、测试缓存、临时日志、构建输出和已确认无用途的临时目录。
- 不删除未提交源码、未追踪文档、数据库、密钥、备份、验收证据、当前功能分支或仍被引用的 worktree。
- 清理 Git worktree 前，核对完整 SHA、分支、`git status --porcelain`、未追踪文件、ahead/behind、远端分支和证据引用。
- `/Users/lmurder/Desktop/api中转站` 中的目录按主源码、开发 worktree、验收副本、规则来源、运行证据和历史归档分类；不能仅因目录名含“副本”“旧”或“测试”而删除。
- 旧压缩包、视频、空目录和 `.DS_Store` 可以作为优先候选，但仍需先核对哈希、引用和是否包含本地数据库或凭据。

## 6. 交付记录

每次完成后保留一份脱敏记录，至少包含：

```text
功能 / 版本 / 源码 SHA：
功能容器验收：状态、镜像 Tag、digest、证据目录
主项目集成验收：状态、候选 SHA、镜像 Tag、证据目录
CI 发布：Tag、源码 SHA、镜像 digest、构建结果
OrbStack 最终验收：状态、容器名、端口、挂载、未验证边界
Linux 上线：用户确认、服务器、时间、回滚版本
清理结果：删除的容器/镜像/缓存，保留的镜像/卷/证据
```

任何未运行、失败、超时、环境阻塞或未验证边界都必须如实记录，不能用“容器启动成功”替代功能验收。
